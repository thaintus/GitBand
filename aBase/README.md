# aBase 目录使用指南

本目录用于统一管理项目开发过程中需要长期维护和持续参考的文档资料。

在进行需求分析、方案设计、功能开发、代码修改、数据库调整或问题排查时，应根据当前任务内容，优先查阅并维护对应目录中的资料，避免将不同职责的文档混合存放。

## 目录结构

```text
aBase/
├─ doc/          # 设计资料、第三方对接资料及其他开发参考文档
├─ iteration/    # 项目迭代文档
├─ sql/          # 数据库表结构及数据库变更 SQL
├─ trash/        # 回收目录，存放逻辑删除的文件
└─ README.md     # aBase 目录使用指南
```

## doc

用于存放项目的设计资料、第三方对接资料及其他开发参考文档。

主要包括：

- 系统设计、架构设计、技术方案等设计文档；
- 产品需求文档、原始需求说明等需求资料；
- 测试方案、测试规范等测试相关资料；
- 第三方平台、API、SDK、协议等对接文档；
- 其他用于需求分析、技术设计、功能实现和问题排查的参考资料。

### 使用规则

- 原始需求、设计方案、第三方资料等，应存放在此目录；
- 在开始需求分析、方案设计或功能开发前，应优先查阅与当前任务相关的文档；
- 项目实际发生的功能开发、代码修改和版本迭代过程，不在此目录记录，应维护在 `iteration` 目录。

---

## iteration

用于统一存放项目迭代文档，记录项目各业务模块的实际开发、调整和演进过程。

### 使用规则

- 当项目产生新的需求、功能调整或版本迭代时，应根据迭代内容所属的业务模块维护对应文档；
- 若对应模块已有迭代文档，应在原文档中追加本次迭代内容；
- 若对应模块尚无迭代文档，应新建对应的迭代文档；
- 迭代文档应尽量记录需求背景、变更内容、实现方案、涉及文件、接口变更、数据库变更及注意事项；
- 在修改已有模块前，应优先查阅该模块历史迭代记录，避免重复实现、遗漏历史约束或破坏已有逻辑。

---

## sql

用于统一管理项目数据库表结构及数据库变更 SQL。

### 使用规则

- 新增数据库表时，应创建对应的表结构 SQL 文件；
- 修改已有数据库表结构时，应同步更新对应的表结构 SQL；
- 对已有环境需要执行的数据库变更，应追加相应的增量 SQL；
- 数据库相关 SQL 文件统一存放在此目录；
- 在新增字段、修改字段、调整索引或变更表结构前，应先检查此目录中的现有表结构和历史变更。

---

## trash

用于存放项目中不再需要、但暂不进行物理删除的文件，相当于逻辑删除的回收站。

### 使用规则

- 当文件不再需要时，应将其移动到本目录，而非直接删除；
- 移入本目录的文件保持原有文件名，便于需要时查找和恢复；
- 本目录中的文件不作为开发参考依据，仅作追溯保留；
- 定期清理本目录中确认无需保留的文件。

---

## 使用原则

处理项目任务时，按以下规则选择需要查阅或维护的目录：

| 场景                     | 目录          |
|------------------------|-------------|
| 查看原始需求、设计方案、接口说明、第三方文档 | `doc`       |
| 查看某个模块过去做过哪些开发和修改      | `iteration` |
| 记录本次功能开发、需求调整或代码变更     | `iteration` |
| 查看当前数据库表结构             | `sql`       |
| 新增或修改数据库表结构            | `sql`       |
| 保存第三方 API、SDK、协议等资料    | `doc`       |
| 文件不再需要，暂不物理删除          | `trash`     |

### 核心判断原则

- **“依据什么开发”**：查看 `doc`；
- **“之前开发过什么、这次改了什么”**：查看或更新 `iteration`；
- **“数据库当前是什么结构、需要怎么变更”**：查看或更新 `sql`；
- **“文件不再需要但暂不删除”**：移入 `trash`。

不应在没有检查相关目录资料的情况下，仅根据代码推测项目约定。若文档与代码存在明显冲突，应结合当前代码、最新迭代记录及相关设计资料综合判断，并在必要时同步更新对应文档。
